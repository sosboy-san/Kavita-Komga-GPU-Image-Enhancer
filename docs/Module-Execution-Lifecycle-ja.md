# GPUモジュールの実行・失効管理（開発版）

基準版は main `1d6844a`（0.9.6）。開発ブランチは `feature/module-execution-lifecycle`。Chromeウェブストア公開前調査の最小変更案1〜3を実装する。公開API・画像処理アルゴリズム・拡張ID・Manifestの権限とCSPは変更しない。

## 実行場所

| 経路 | 登録・評価 | 画像処理 |
| --- | --- | --- |
| インポート検査 | 既存の検査Sandboxでユーザー指定コードを評価・検証 | 実画像処理なし |
| Workerモード | MAINには保存済みメタデータから候補を構築。外部コードを事前評価しない。ジョブの選択モジュールをSandbox内Workerで評価 | 同Workerの既存GPUホスト |
| 速度優先：追加コード | 選択中のレンダラー・前／後フィルターだけを既存の `userScripts.execute({world:'MAIN'})` で登録 | 登録したcreate/prepare/executeを既存MAINホストから呼ぶ |
| 速度優先：同梱フィルター | 選択中のものだけを拡張内の固定ファイルから読み込む | 同じMAINホスト・公開API |

背景処理や候補ローダーではユーザーコードを評価しない。MAINに渡す処理用ソース文字列は既存構造として残す。コード文字列の存在と評価は別であり、この変更は文字列の秘匿を目的にしない。

`background/module-runtime.js` がモード、有効状態、読書URL、選択IDとstamp、ユーザースクリプト許可から実行状態を作る。`service-worker.js:syncRuntimeModules()` に準備を集約し、状態が同じなら再評価を省く。状態変更時は先に処理を中断し、古い実行記述子を捨ててから準備する。準備の途中に設定・許可が変わった場合は利用可能にしない。

## 失効とキャッシュ

- 更新は登録IDを維持し、新しいinstallation stampを発行する。削除は選択・候補・パラメーター・表示名も既存管理処理で整合させる。
- モード・選択・stamp・許可の変更は実行状態を変え、処理クライアントの中断、ホスト破棄、Coreの画像／先読みキャッシュ無効化へ接続する。既存の画像URL借用・解放処理には変更を加えない。
- ホスト破棄時にモジュールのdisposeを試行する。実行中・失われたコンテキストでは最後にホスト全体を破棄する。Worker強制終了時はWorkerの終了で資源を解放し、ユーザーのdispose完了は保証しない。
- 独自追加コードを選択している間は、ジョブごとにISOLATED bridge→背景処理でID、stamp、documentId、現在URL、サイト権限、許可状態を再確認する。同梱フィルターだけならこの追加往復は行わない。
- bridgeは選択中の追加コードについて約1秒ごと、および復帰・フォーカス時にも許可を確認する。取消検知時は実行記述子を捨てて表示処理を中断する。ブラウザーの停止・タイマー抑制中の即時検知は保証しない。既に実行した副作用の取消や、MAINを占有する同期コードの強制停止もできない。
- 拡張更新前の処理クライアントが残るタブには再読み込みを要求する。古い実行経路へ継続接続しない。
- 起動完了はreadinessフラグと実際のCoreの両方で判定する。起動途中の失敗後は未登録候補を捨て、準備状態も失効させて再構築する。基盤ファイルの読み込みに失敗した場合は、完了フラグを公開せず元の失敗を報告する。
- 認可の失敗通知は実行状態のキーと要求時のインスタンスに対応付ける。モード切替前の要求や、別モードを経由して同じ設定へ戻った際の古い要求で、新しい状態を失効させない。現在のインスタンスに対する実際の許可取消は従来どおり失効させる。

## 付属フィルター

USM・紙地復元・カラー判定付き線色／濃度調整を初回登録する。新しいフィルターの適用はOFF。既存の同IDモジュール、バージョン、選択、stampは維持する。候補枠の既存上限も維持する。

初回登録済みマーカーにより、削除したフィルターを復活させない。公式ファイルから再登録できるよう、USMの配布用.txtも追加した。同梱ファイルとして扱えるかは背景処理がSHA-256とメタデータの一致で判定し、UIの自己申告を信用しない。ソースが異なるファイルは通常の追加コードとして扱う。

- `background/default-packages.js`、`modules/default-filters.js`、`modules/defaults/*`、`build-default-filters.cjs`：初回登録・削除永続化・同梱コード照合。
- `background/module-runtime.js`、`background/service-worker.js`：メタデータ候補、選択限定登録、実行状態・ジョブ認可。
- `modules/module-loader.js`：関数登録を必要としないレンダラー候補。
- `content/main.js`、`content/bridge.js`、`gpu/processing-client.js`：認可往復、取消監視、中断。
- `gpu/main-runtime.js`、`gpu/worker-runtime.js`、生成物 `gpu/worker-source.js`：破棄処理、管理対象USMを同梱の旧記述子より優先。
- `content/reader-core.js`：正常な中断時の待機・元画像復帰・再実行。
- `tests/*` の追加・更新、`reference-packages/*`、本資料と `BUILDING.md`。

GPUホスト、LoHalo Jr.／NoHalo Jr.、USMの演算、公式2フィルターのソース、モジュール契約、ページ送り・全画面・詳細設定表示の実装は変更しない。Reader Coreの変更は中断時のエラー処理に限定する。

## 検証と限界

自動検証では、実際の背景処理を使い、Worker時に選択・未選択のコードがMAINで一度も評価されないこと、速度優先は選択したものだけを評価することをカウンターで確認する。変更なしの再準備、更新・削除・OFF、許可取消／復元、準備途中の取消、現在の読書URL、全付属フィルターの削除／復元と同梱判定も検証する。

ブラウザーフィクスチャは実際のChromium MAIN/ISOLATED、Sandbox CSP、Worker、WebGLを使う。chrome.* APIは実背景処理へ接続するモックであり、インストール済み拡張のAPI動作やAndroid Edgeそのものを検証したものではない。

実施結果：コア28件成功。既存ブラウザー回帰29件成功（Kavita／Komga、ページ送り、全画面、詳細設定、公開API、解析、資源管理など）。別の1件 `usm-memory-browser.cjs` はリポジトリ外の旧実装 `../phase3-active-fix/extension/gpu/usm.js` がなく実行不能で、比較を省略して成功扱いにはしない。追加の実行経路ブラウザーテストはPC幅・タッチ幅の両方で成功した。追加確認の1回は既存CPU解析の2秒期限を超え、同条件の再試行と最終確認は成功した。ソフトウェアGPU・負荷下での期限に余裕があることまでは保証しない。

実機報告後、起動経路のテスト不足を補う `module-startup-browser.cjs` を追加した。背景処理のHELLOから実際のCoreまで通し、Kavita／Komga×PC幅／タッチ幅×Worker／速度優先の8条件を検証する。起動中断後に候補が変わると、修正前には古い候補が残って `Provider registration mismatch` を再現でき、修正後は再接続できる。正常な初回起動、変更なしの再接続、稼働中の追加・削除、基盤読み込み失敗、Coreを伴わない完了フラグ、旧クライアントの再読み込み要求も対象とする。初回の実行経路テストはCoreをスタブにしていたため、この起動不整合を検出できていなかった。

続く実機報告の `expected:["lohalo","nohalo"], actual:null` については、Coreが登録用一時一覧を消費・削除した後も、確認処理がその一覧を必須としていた。起動前は一時一覧とAPI版、起動後はCoreの登録済みIDとカタログを照合するよう修正した。登録欠落・余分なID・重複IDはエラーとして維持する。Coreの登録が不整合なら、一時一覧が正常でも成功扱いにしない。

この修正の検証はコア29件成功、起動テスト8条件成功。一時一覧消費後の再確認、別の接続がCoreを初期化した後に古い起動判定が届く重なり、登録済み作品詳細ページからの接続を追加した。`7bef5a8` のソースでは重なる接続から `actual:null` を含む同じエラーが発生することを確認し、修正後は成功した。これは実機の内部タイミングを直接観測したものではない。製品コードの変更は `content/providers-ready.js` の確認処理に限定し、画像処理・権限・CSPは変更しない。

その後の `Extension context invalidated`／`chrome.runtime.getURL` 参照エラーには、接続失効時の後始末を追加した。背景処理への送信をasyncラッパーに通して同期例外も捕捉し、runtimeの失効を検知した接続は、未完了要求・ポート・Worker iframe・タイマー・イベントリスナーを解放する。MAINには現在の接続IDで通知し、該当する処理と読書Coreを停止する。別の接続IDから届く古い失効通知は無視する。一時的な背景通信エラーでは恒久失効させず、再接続を可能にする。

Worker接続要求にも接続IDを付け、古いbridgeが新しい接続のポートを受け取らないようにした。公開GPU APIとは別の内部接続版を3へ更新し、旧クライアントの残るタブには再読み込みを要求する。詳細設定を閉じる際の通知も同期例外をPromiseで扱い、UIの片付けが中断しないようにした。保存済み設定・GPU演算・Manifest・権限・CSPは維持する。

追補の検証はコア30件、起動8条件、実Worker／MAIN処理と失効のPC幅・タッチ幅、設定オーバーレイのKavita／Komga・PC幅／タッチ幅。runtime消失、getURL/sendMessageの同期例外、後始末、古い接続の無視、一時的な通信失敗からの復帰を検証する。`9254c4a` ではruntime消失時にgetURL参照エラーとなることも確認した。実機での拡張更新そのものを自動化した試験ではない。修正版へ更新した後も、更新前から開いている読書タブは再読み込みして旧スクリプトを入れ替える必要がある。

さらに作品詳細→読書のSPA遷移では、詳細画面で作った「読書中でない」準備状態が更新されない経路があった。MAINの既存監視からパス変更も通知し、bridgeが準備を更新する。同時要求はまとめ、準備中に到着した画像ジョブは完了を待つ。準備済みジョブには準備用の追加IPCを入れない。モード・選択と一致しない古いジョブは中断し、新しい設定での処理を優先する。

背景側の認可状態を保存する前にMAINでreadyが見える競合も修正した。背景状態の保存→MAINでのready公開→Coreの再処理通知の順にする。保存を意図的に止めたテストでは、保存完了までMAINが利用不可のままであることを確認する。内部接続版は4。公開GPU APIは変更しない。

Reader Coreのエラー分岐も、正常な `ANALYSIS_CANCELLED` を待機・再実行として扱うようにした。元画像へ戻す既存の処理と、epoch変更時の再実行を維持する。権限拒否、モジュール例外、タイムアウト等の実際の失敗は従来どおり報告する。

`reader-spa-runtime-browser.cjs` は実際の背景処理・MAIN・ISOLATED bridge・Core・Sandbox/Worker・GPU処理を通し、詳細→読書→詳細→再読書の2回とも処理済みBlob画像になること、レンダラーID・出力寸法を確認する。Kavita／Komga×PC幅／タッチ幅×Worker／速度優先×LoHalo／追加Lanczos3の16条件で、USM付き表示が成功し、未捕捉例外と `[crisp-images]` 警告は発生しなかった。Workerで追加レンダラーがMAIN評価されないことも確認する。`0d1d5a9` では同じ遷移で `Module runtime is not ready` が発生し、GPU画像にならないことを再現した。APIとサーバー応答はフィクスチャであり、実機試験ではない。

続く設定反映の報告では、進行中の接続確認に新しい設定変更のPINGが合流し、古い確認結果で変更通知まで完了扱いになる競合を再現した。保存値をNoHaloへ変更しても、読書側の設定・実行状態がLoHaloに残る。前版76b8279では、この状態から前処理をONにすると、取りこぼしたレンダラー変更も反映されることまで再現した。

明示的なPING／準備要求は、古い確認を待ってから最新設定を取得し直すよう修正した。通常の表示中に定期取得を追加する変更ではない。内部接続版は5。演算・GPU API・権限・CSP・キャッシュ実装は変更しない。

## 残るChromeウェブストア審査上の論点

今回の変更は審査通過の保証ではない。ユーザー指定コードの検査Sandbox／Workerでの評価は残る。速度優先も、User Scripts APIからMAINへ登録したコールバックを通常のMAINホストから呼び出す構造を残しており、この範囲が例外に収まるかの説明と審査が必要。同梱化された3フィルター以外の追加コードを、一律に同梱コードと説明してはならない。

Sandboxの隔離とメッセージ境界、ユーザー指定コードの取り扱い、権限理由・プライバシー申告・ライセンス・ストア向け配布内容の最終確認は引き続き必要。Manifest、CSP、権限、公開IDを今回変更していないことは、それらの審査適合を証明しない。

## 実機確認

### 9254c4aとの比較で確認したレンダラー判定の退行

動作確認済みと報告された `9254c4a` と後続版を比較した。`76b8279` で追加した処理開始判定が、実際のジョブの `provider` ではなく、非同期CONFIG通知で更新される `settings.renderer` を実行状態と比較していた。Coreは先にローカルのレンダラー選択を変更するため、両者は一時的に異なり得る。この状態で正常なジョブを `ANALYSIS_CANCELLED` と誤判定する。逆に、設定値だけが新しく実ジョブが古い場合には中断できていなかった。

修正は `gpu/processing-client.js` の比較対象を `provider` にすることに限定した。モード・前処理・後処理・許可・ID/stampの確認は維持し、Coreの中断後処理やキャッシュは変更しない。GPU公開API、演算、画像形式、Manifest、拡張IDも変更しない。

実GPU処理を行うChromiumフィクスチャで、LoHaloからNoHaloへ更新済みのジョブと古い設定値を組み合わせた場合、`9254c4a` と `0d1d5a9` は処理完了、`76b8279` と `fded207` は中断、比較対象だけを直した版は旧版と同じ復号画素ハッシュになった。実ジョブだけが古い逆の条件は修正版で中断する。Worker／速度優先、PC幅／タッチ幅の回帰テストにも同じ確認を追加した。

実際のReader Coreを使う試験でも、前処理OFF・USM後処理ONで、Coreと実行状態はNoHalo、設定値のみLoHaloに保った状態を注入した。キャッシュにないUSM値で再処理し、変更前は表示完了を待ってタイムアウト、修正後は両モードでNoHaloの縮小済みBlob表示が完了した。これは非同期状態を制御したフィクスチャであり、ユーザー端末の発生タイミングを直接記録したものではない。

別途、中断処理を9254c4aに戻すだけの比較も行ったが、制御した中断条件からの復帰は旧版・現行版とも成功しなかったため、今回の退行の根拠にはしない。これまでのフィクスチャ成功のみで実機の症状解消を断定した判断は不十分だった。今回も端末での解消確認は別途必要となる。

PC Chrome・Android Edgeで、組み込みのみ／同梱フィルター／独自レンダラー／独自フィルターを両モードで確認する。ページ移動・先読み中のモード変更、フィルター更新・削除、許可取消／復元、背景復帰、GPUコンテキスト喪失、拡張更新後の再読み込みも確認する。画像・ページ送り・設定UIの既存挙動、処理時間・メモリ・元画像への復帰を記録する。
